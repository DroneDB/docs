The DroneDB library, `libddb` (`libddb.so` on Linux, `ddb.dll` on Windows), does the indexing, builds, tiles, thumbnails and raster analysis behind the `ddb` command line and Registry. Programs use it through its C API, declared in `ddb.h`. Registry calls it from .NET with P/Invoke; any language with a C foreign-function interface can do the same.

This page is for integrators who load the library themselves. The `ddb` command line contains the library and needs none of this.

## Versions and ABI

The library, its C ABI and the release have **one version**, the `version` of DroneDB's `package.json` (2.2.0 for this release). It is written into the generated header `ddb_version.h`:

| Macro | Value in 2.2.0 |
|-------|----------------|
| `DDB_VERSION_MAJOR`, `DDB_VERSION_MINOR`, `DDB_VERSION_PATCH`, `DDB_VERSION_STRING` | `2`, `2`, `0`, `"2.2.0"` |
| `DDB_ABI_MAJOR`, `DDB_ABI_MINOR` | `2`, `2` (the major and minor of the version) |

The ABI follows semantic versioning: a removed or changed export needs a new major version, a new export at least a new minor. Within a major version the C ABI only grows, and the JSON outputs only gain fields. A host that needs an export or a field of a later minor version checks `DDBGetAbiVersion()` first (`DDBGetAbiVersion() >> 16` is the major, the low 16 bits are the minor, so 2.2 is `0x00020002`). What each minor version added:

| ABI | Release | Added |
|-----|---------|-------|
| 2.0 | 2.0.0 | The first 2.x C API |
| 2.1 | 2.1.0 | `DDBAlignRasterEx`, `DDBMergeMultispectralEx` and `DDBMaskBordersEx`, which take an options struct with `overwrite` ([Output files](#output-files)) |
| 2.2 | 2.2.0 | `DDBRasterOptions` and ten raster value exports that take it ([Raster values](#raster-values)), and the build key of every build ([Build key](#build-key)) |

Every release publishes, next to the `.deb` and the Windows zip:

| Asset | Content |
|-------|---------|
| `ddb.h` | The C API (valid C11 and C++) |
| `ddb_export.h` | The export macro `DDB_DLL`, one file for every platform |
| `ddb_version.h` | The version macros above |
| `ddb.symbols` | The list of exported functions |
| `SHA256SUMS` | The SHA-256 of every asset |

The library exports exactly the functions listed in `ddb.symbols` (109 in 2.0.0, 112 in 2.1.0 and 122 in 2.2.0) and nothing else; its C++ classes and functions are internal. Pin a release by version and SHA-256, and build against that release's headers.

## Start-up and shutdown

A host checks the library before it uses it, configures it, then registers the process:

```c
#include <ddb.h>

int start_ddb(void) {
    uint32_t abi = DDBGetAbiVersion();               /* callable before DDBRegisterProcess */
    if ((abi >> 16) != DDB_ABI_MAJOR) return -1;     /* another major version: refuse */
    if ((abi & 0xFFFF) < 2) return -1;               /* this host calls 2.2 exports: refuse 2.0 and 2.1 */

    const char *caps = DDBGetCapabilities();         /* JSON: abi, version, errorCodes, errorReasons,
                                                        cancellable, symbols; owned by the library */
    (void)caps;

    if (DDBConfigure("{\"cpuPoolSize\": 6, \"gdalCacheMb\": 512}") != DDBERR_NONE) return -1;
    /* optional: DDBSetLogCallback(cb, minLevel, user) to receive the native log records */

    if (DDBRegisterProcess(false) != DDBERR_NONE) {  /* a failed initialization is final */
        /* DDBGetLastError() has the reason */
        return -1;
    }
    return 0;
}
```

When the host stops, after it has stopped sending work, it calls `DDBShutdown(timeoutMs)`: new calls are refused with `DDBERR_SHUTDOWN`, the calls in flight are asked to stop and are waited for, the pooled index connections are checkpointed and closed, and the log is flushed.

Registry runs this sequence at start-up and refuses to start when the library is not ABI 2.2 or later (DroneDB 2.2.0), or lacks an export it calls. The message names the ABI that it needs.

## Process configuration

`DDBConfigure(json)` sets process-wide settings; `DDBGetEffectiveConfig` returns the settings in effect, where each one comes from (`configure`, `environment` or `default`) and the core count. Each setting takes the `DDBConfigure` value, else its environment variable, else the default. A value of `null` puts a setting back to its environment variable or default. An unknown name or an invalid value returns `DDBERR_INVALIDARGS` and changes nothing. Call it before `DDBRegisterProcess`; it can also be called later, and a change applies to the work that reads the setting afterwards.

| Setting | Environment variable | Default | Meaning |
|---------|----------------------|---------|---------|
| `cpuPoolSize` | `DDB_CPU_POOL_SIZE` | cores − 1 | Worker threads the library may run at once beside the calling threads, across every call (parallel indexing, GDAL threads, PDAL readers, Obj2Tiles, untwine). `0` runs every call on its calling thread only. |
| `ioThreads` | `DDB_IO_THREADS` | `4` | Threads of one disk-bound section (hashing the files of a delta, deleting build folders). |
| `minFreeDiskMb` | `DDB_MIN_FREE_DISK_MB` | `512` | Free MiB a build or a copy of build artifacts needs on the volume it writes to; below it the call fails with the reason `lowDiskSpace`. `0` turns the check off. |
| `gdalCacheMb` | `DDB_GDAL_CACHE_MB` | `1024` | Size in MiB of GDAL's block cache, shared by the whole process (tiles, renders, thumbnails, statistics, builds); 16 to 1048576. Set with `DDBConfigure`, it is the size of the cache at once, raising or lowering GDAL's own default (5 % of the RAM) and winning over `GDAL_CACHEMAX`. From the environment or the default it is an upper bound only: `DDBRegisterProcess` lowers GDAL's cache to it, never raises it, and leaves an explicit `GDAL_CACHEMAX` alone. A build in flight keeps the cache it asked for (`DDB_COG_CACHE_MB`) until it ends. |
| `cacheDir` | `DDB_HOME` (then `$DDB_HOME/.ddb`) | `~/.ddb` | Absolute folder where the library caches thumbnails, tiles, index templates and DSM tiles. The registry credentials of the `ddb` command line stay in the profile folder. |

Environment variables are read strictly: digits only, so `1024MB` is ignored and the default applies. The other environment variables of the library (index connections, COG builds, renders) are listed in the [CLI reference](/developers/cli/reference.mdx#environment-variables).

## Errors

Every export returns a `DDBErr`:

| Code | Value | Meaning |
|------|-------|---------|
| `DDBERR_NONE` | 0 | Success |
| `DDBERR_EXCEPTION` | 1 | Failure; see the message |
| `DDBERR_BUILDDEPMISSING` | 2 | A build waits for a missing companion file |
| `DDBERR_BUILDINPROGRESS` | 3 | Another build of the entry is running |
| `DDBERR_CANCELED` | 4 | Canceled by the progress callback or a cancel token |
| `DDBERR_BUSY` | 5 | The index is busy |
| `DDBERR_NOTFOUND` | 6 | Not found (`DDBGet` of a missing path) |
| `DDBERR_INVALIDARGS` | 7 | Invalid arguments: a client error |
| `DDBERR_RETRYABLE` | 8 | A temporary condition; `DDBGetLastErrorReason()` says which (`lowDiskSpace`, `noSpaceOnDevice`, `idleTimeout`) |
| `DDBERR_SHUTDOWN` | 9 | The library is shutting down |

After a failure, read `DDBGetLastError()` (the whole message, UTF-8) and `DDBGetLastErrorReason()` on the same thread, before any other call: the last error belongs to the calling thread and is cleared when a call starts. A failed call leaves its output pointers untouched or NULL; outputs are written only on success. `DDBERR_INVALIDARGS` and `DDBERR_RETRYABLE` are returned by the exports added in 2.0; the older exports keep the codes they returned in 1.x (`DDBERR_EXCEPTION` with the same reason), except for a refused entry path (below), a canceled token and a shutdown, and the raster queries of 2.1 and 2.2: a formula that does not exist, or a place without data, is `DDBERR_INVALIDARGS`.

## Entry paths

An entry path is a path inside a dataset, relative to its root (`photos/a.jpg`), as the index stores it. Every export that takes one applies the rule of `DDBNormalizePath`:

- `\` and `/` both separate segments; `.` segments and repeated or trailing separators are dropped, so `a\b`, `./a//b/` and `a/b` name the same entry;
- a path that is absolute (a leading `/` or `\`, or a drive such as `C:`), has a `..` segment, names the reserved `.ddb` folder or its NTFS short name (`ddb~` and digits, such as `DDB~1` or `ddb~2`, in any case, on every platform) at any depth, or is not valid UTF-8 is refused: the call returns `DDBERR_INVALIDARGS`, changes nothing, and the last error reads `Invalid <argument> '<path>': <code>` (`absolute`, `traversal`, `reserved`, `encoding`, `empty`).

This applies to `DDBGet`, `DDBListEntries` and `DDBListEntriesEx` (folder; `""` and `"."` are the root), `DDBSearch`, `DDBMoveEntry`, `DDBBuild` (source), `DDBIsBuildable`, `DDBIsBuildActive`, `DDBIsBuildComplete`, `DDBGetBuildStatus`, `DDBGetBuildArtifacts`, the `DDBMeta*` exports (and the rows of `DDBMetaRestore`), `DDBStac` and `DDBStacData`, `DDBResolveBuildFile`, and every path inside a delta (`DDBApplyDelta`, `DDBApplyDeltaEx`, `DDBComputeDeltaLocals`). It also applies to the exports that existed in 1.x, whose other invalid arguments still return `DDBERR_EXCEPTION`.

Filesystem paths are not entry paths and keep their meaning: the files `DDBAdd`, `DDBAddWithOptions` and `DDBAddWithHints` add, the paths of `DDBRemove`, `DDBList` and `DDBInfo`, dataset folders, output files and `DDBBuild`'s destination.

Call `DDBNormalizePath(path, reservedJson, &out)` to check or normalize a path before using it (it answers `{"path": "<normalized>"}` or `{"rejected": "<code>"}`); `reservedJson` adds names reserved as the first segment (Registry reserves its own upload folder this way). DroneDB keeps the expected results of more than 70 inputs in `tests/contract/vectors/entry-paths.json`, so a host can test that it rejects the same paths.

## Cancellation

A cancel token stops the work of a call from another thread:

1. `DDBCreateCancelToken(&token)`, one per request or job;
2. `DDBSetThreadCancelToken(token)` on the thread that makes the call, right before it (the next call takes it; set it again before every cancellable call);
3. `DDBCancel(token)` from any thread: the call stops at its next checkpoint and returns `DDBERR_CANCELED`;
4. `DDBFreeCancelToken(token)` when the host no longer needs it.

The `cancellable` list of `DDBGetCapabilities()` names the exports that honour a token. In 2.0.0 there were 29, in 2.1.0 30 and in 2.2.0 there are 40:

- tiles, renders and thumbnails: `DDBTile`, `DDBMemoryTile`, `DDBMemoryTileEx`, `DDBMemoryTileEx2`, `DDBMemoryTileFmt`, `DDBRenderRasterRegion`, `DDBRenderRasterRegionEx`, `DDBRenderRasterIndex`, `DDBGenerateThumbnail`, `DDBGenerateMemoryThumbnail`, `DDBGenerateMemoryThumbnailEx`, `DDBGenerateMemoryThumbnailEx2`;
- exports and builds: `DDBExportRaster`, `DDBExportRaster2`, `DDBExportRaster3`, `DDBBuild`, `DDBBuildEx`;
- raster analysis: `DDBGetRasterMetadata`, `DDBGetRasterValueInfo`, `DDBGetRasterValueInfoEx`, `DDBGetRasterPointValue`, `DDBGetRasterPointValueEx`, `DDBGetRasterPointValuePixelEx`, `DDBGetRasterAreaStats`, `DDBGetRasterAreaStatsEx`, `DDBGetRasterAreaStatsPixelEx`, `DDBGetRasterProfile`, `DDBGetRasterProfileEx`, `DDBCalculateVolume`, `DDBDetectStockpile`, `DDBDetectAllStockpiles`, `DDBGenerateContours`, `DDBGenerateContoursEx`, `DDBMaskBorders`, `DDBMaskBordersEx`;
- Gaussian splats: `DDBExportSplatSpz`, `DDBExportSplatTrainingData`;
- deltas: `DDBComputeDeltaLocals`, `DDBApplyDelta`, `DDBApplyDeltaEx`.

A canceled call leaves no partial output (a canceled `DDBMaskBorders` or `DDBMaskBordersEx` writes no file, and keeps the file it would have replaced). `DDBApplyDelta` and `DDBApplyDeltaEx` are atomic to a cancel: they stop while they read and hash the added files, with the dataset and the source files as they were, and once they start to change the dataset they apply the delta whole and return `DDBERR_NONE`.

## Output files

An export that writes a data file refuses to replace one that exists, and refuses an output that is one of its inputs. Since 2.1 this holds for `DDBAlignRaster`, `DDBMergeMultispectral` and `DDBMaskBorders`, as it does for the [`ddb` commands](/developers/cli/cookbook.mdx#existing-outputs): a call whose output exists returns `DDBERR_EXCEPTION` and leaves the file as it is. A host that replaces an output on purpose calls the variant that takes options:

| Export | Options struct |
|--------|----------------|
| `DDBAlignRasterEx(source, reference, output, mode, options, &result)` | `DDBAlignRasterOptions` |
| `DDBMergeMultispectralEx(paths, numPaths, output, options)` | `DDBMergeMultispectralOptions` |
| `DDBMaskBordersEx(input, output, near, white, options)` | `DDBMaskBordersOptions` |

The three structs have the same 8 bytes: `uint32_t structSize` (set it to `sizeof` of the struct), `bool overwrite` (true replaces an output that exists, false refuses it) and `uint8_t reserved[3]`, which must be 0. A later version may append fields; a library that does not know a field refuses a struct whose unknown bytes are not zero. The variants return `DDBERR_INVALIDARGS` for a `NULL` options pointer, a `structSize` below 8, a non-zero reserved byte, or an output that is one of the inputs (with or without `overwrite`).

The output is written beside the final path, in a private folder, and put in place with one rename when it is complete. A failed or canceled call therefore leaves the file that it would have replaced as it was, and `DDBMaskBordersEx` with `overwrite` removes the stale `.msk` of the replaced file. The old exports keep their signatures, so move a host to 2.1 together with its switch to the variants: Registry calls only the variants and asks for the replace only when the output exists at the moment it decides (a file that another writer creates in the meantime is refused and kept).

## Builds

`DDBBuild(ddbPath, source, dest, force, pendingOnly)` builds the derivative products of an entry. `DDBBuildEx(ddbPath, source, dest, force, pendingOnly, optionsJson)` takes the same arguments and a JSON object of options; `DDBBuild` is `DDBBuildEx` without options. The only option is `{"threads": N}`, an integer from 1 to 4096 (not `2.0`, `true` or `"2"`): the most threads each build of the call may use. It only lowers the `DDB_BUILD_THREADS` budget and never raises it. It bounds the GDAL threads of a raster build, the `bm3d` program of a 3D model build, the cores of Obj2Tiles and the PDAL `writers.copc` fallback; Untwine and `build-lod` have no thread option and are not bounded. `NULL`, `""` and `{}` mean no cap. A malformed text, a value that is not an object, any other key, or a `threads` outside the rule returns `DDBERR_EXCEPTION` with a message that names the problem, before anything is built. Registry uses the cap for the [background rebuild](/docs/self-hosting/configuration) of models.

A build that misses a companion file (`DDBERR_BUILDDEPMISSING`) is deferred: the library keeps a pending marker that lists the missing files. Since 2.2 the marker belongs to one entry path (`<key>.<pathId>.pending`), not to the content: two identical OBJ files in two folders each wait for their own `.mtl`, and a move or rename of the entry keeps its marker. `DDBGetPendingBuildInfo` returns each pending build with `hash`, `key`, `path`, `missingDependencies`, `lastAttempt`, `retryAfter` and `awaitingFiles`. A build with `awaitingFiles: true` waits for those files: `DDBBuild` with `pendingOnly` (and no `force`) skips it, and `DDBIsBuildPending` does not count it, so `DDBIsBuildPending` is true only for pending work that a retry can progress. Adding or moving in the file that a missing name stands for releases the build: the name is a dataset-relative path, or a path relative to the folder of the entry, compared ignoring case (the same file name in another folder does not release it). `DDBAdd`, `DDBAddWithOptions`, `DDBAddWithHints`, `DDBMoveEntry` and `DDBApplyDelta` do this, and `DDBCopyBuildArtifacts` releases a copied marker when the destination already has such a file. A pending marker of the layout before the build key (`<hash>.pending`) is moved to the markers of its entries by `DDBRescan`, `DDBRescanEx` and a `DDBBuild` with `pendingOnly`. A released build has no missing files and a `lastAttempt` of 0, so it is due at once. A build that failed for a temporary reason (low free disk space, a full disk, a tool that stopped responding) keeps a marker without missing files and is retried from `retryAfter`.

## Build key

Every entry has a **build key**, which names the folder of its build (`.ddb/build/<key>/`) and the URLs of its files (`.../build/{key}/{path}`). For a type whose build depends on the content only the key is the content hash, as before. For a **model or a Gaussian splat that has a georeference** it is `<hash>-<digest>`, where the digest is 16 hexadecimal characters of the SHA-256 of the entry's `georef` property: the same file builds once for each georeference, so the georeference of one copy never leaks into a copy that has none or another one. Since 2.2:

- the build object (`DDBGetBuildArtifacts`, `DDBListEntriesEx`), `DDBGetPendingBuildInfo` and the answer of `DDBCopyBuildArtifacts` have `key` next to `hash`;
- `DDBResolveBuildFile` and `DDBCopyBuildArtifacts` take the key in their `hash` argument, a malformed one is `DDBERR_INVALIDARGS`, and build URLs and folders are made from `key`, never from `hash`;
- `DDBRescan` and `DDBRescanEx` add `buildKey` and `buildKeyChanged` to each entry they re-read. `buildKeyChanged` is true when the entry has to move to the build folder of its key (a changed file, a changed georeference, and the first rescan after the upgrade of a model or a splat that has a georeference). A host rebuilds only these entries; the other entries keep their builds.

A host that moves from 2.1 checks `DDBGetAbiVersion()` for 2.2 or later before it reads `key` or calls a 2.2 export, rescans after the upgrade, and rebuilds the entries whose `buildKeyChanged` is true. Registry does this in a background job at the first start with the new version, one dataset at a time, and records each dataset that is done.

## Build manifest

The library owns the layout of build outputs, the build state and the rules of each entry type. A host serves what these exports return and never composes a build path itself:

| Export | Returns |
|--------|---------|
| `DDBGetEntryTypes` | Every entry type: `id`, `name`, `buildable`, `thumbnail` (`none`, `file`: rendered from the file, `build`: from an artifact once built), `sidecarExtensions`, `roles` |
| `DDBGetBuildArtifacts` | For many entries with one index open: `buildable`, `key`, `state` (`none`, `pending`, `building`, `complete`), `missingDependencies`, `awaitingFiles` (the pending build waits for those files, as in `DDBGetPendingBuildInfo`), `lastAttempt`, `retryAfter` (Unix seconds from which a pending build that waits for no file is retried), `root` and the artifacts that exist |
| `DDBListEntriesEx` | A listing with the same build object per entry (option `withBuild`) |
| `DDBResolveBuildFile` | A file of a build, checked (`.../build/{key}/{path}`, tiles included; its `hash` argument takes the build key), as `{"path": "<absolute path>", "mediaType": "<type>", "version": "<version>"}`; `mediaType` is the artifact's when the file is the one a client opens (a file artifact or the index of a directory artifact) and is absent for any other file, such as a tile; `version` is the current version of the artifact the file belongs to (a tile has the version of its directory) |
| `DDBCopyBuildArtifacts` | Copies an entry's build, with its pending marker, to another dataset; its `hash` argument takes the build key, and its answer is `{"hash", "key", "artifacts", "pending"}` |

An artifact is `{role, path, kind, mediaType, downloadName?, index?, legacy?, fallbackFor?, version}`: `path` is relative to the build root, `kind` is `file` or `dir` (`index` names the descriptor of a directory), `downloadName` is set for downloadable artifacts (a directory is offered as a ZIP archive of what is in it, under that name). `version` is an opaque lowercase hex string that identifies the bytes of the file a client opens (the file, or the index of a directory) as they are now: it changes whenever a build rewrites or replaces that file under the same key, such as a forced rebuild or a rebuild to a newer layout. Compare it, never parse it. A host can put it in the URL of the artifact and let clients keep what that URL returns while `DDBResolveBuildFile` still reports the same version. A `legacy: true` artifact is the output of an older build layout. Its `fallbackFor` names the role it stands in for, and the artifact is listed only while that role is missing, so a client that reads the roles in its order of preference shows the old output until a rebuild writes the new one. Roles say what an artifact is for, never where it is, and are only ever added: pass an unknown role through.

| Role | Artifact | Media type |
|------|----------|------------|
| `raster.cog` | Cloud Optimized GeoTIFF of a GeoRaster | `image/tiff; application=geotiff; profile=cloud-optimized` |
| `vector.gpkg` | GeoPackage of a vector | `application/geopackage+sqlite3` |
| `vector.mvt` | Mapbox Vector Tiles (directory; index: the TileJSON) | `application/json` |
| `vector.local` | Drawing-coordinate metadata of a CAD drawing without a CRS | `application/json` |
| `pointcloud.copc` | Cloud Optimized Point Cloud | `application/vnd.laszip+copc` |
| `pointcloud.ept` | Entwine Point Tiles of datasets built before COPC (legacy, read only; `fallbackFor: "pointcloud.copc"`) | `application/json` |
| `model.bm3d` | bm3d multiresolution 3D model (`bm3d/model.bm3d`) | `application/vnd.dronedb.bm3d` |
| `model.nexus` | Nexus multiresolution mesh of models built before bm3d (`nxs/model.nxz`; legacy, read only; `fallbackFor: "model.bm3d"`) | `application/octet-stream` |
| `model.3dtiles` | OGC 3D Tiles (directory; index: `tileset.json`; downloadable as `model.3dtiles.zip` for a model, not for a `.3tz`) | `application/json` |
| `gsplat.lod` | Level-of-detail Gaussian Splat (`gsplat/model.rad`, streamed with range requests) | `application/octet-stream` |
| `gsplat.spz` | SPZ Gaussian Splat of builds before the RAD layout (`gsplat/model.spz`; legacy, read only; `fallbackFor: "gsplat.lod"`) | `application/octet-stream` |
| `gsplat.bounds` | Bounding box of the splats to frame the first view, with the estimated `up` and, for a georeferenced splat, its `wgs84Footprint` (`gsplat/bounds.json`; optional) | `application/json` |
| `gsplat.export` | `.spz` of a splat for other tools, made on demand by `DDBExportSplatSpz` (`gsplat/export.spz`; listed only while it exists, not legacy, not part of a complete build, removed by a rebuild) | `application/octet-stream` |

A rebuild of a model writes `bm3d/` and removes `nxs/` only after `bm3d/` is published, and a failed rebuild keeps `nxs/`, so a model stays viewable while it is rebuilt.

Registry passes these artifacts to clients as `artifacts: [{role, url, mediaType}]` on each entry.

## The .spz of a Gaussian splat

`DDBExportSplatSpz(ddbPath, entryPath, &output)` converts the dataset file of a built Gaussian splat to one `.spz` for other tools and keeps it in the build folder of the entry as the artifact `gsplat.export` (`gsplat/export.spz`, download name `export.spz`). `output` is a JSON object, to free with `DDBFree`: `{"path": "<absolute path of the .spz>", "role": "gsplat.export", "cached": true}`. `cached` is true when the file already existed, was not empty and was not older than the dataset file, and it is then returned as it is; otherwise it is converted again.

- The entry must be a Gaussian splat in a format that is converted (PLY, SPLAT or SPZ) and must have been built (`model.rad` exists). The file is made on demand and never by a build.
- The call takes the build lock of the entry: it returns `DDBERR_BUILDINPROGRESS` while a build of the entry, or another export of it, runs.
- The conversion reads the whole file and decodes all the splats in memory, so count a few times its size for the peak and call it as a heavy task. No size is refused.
- The file is written atomically. A forced rebuild of the entry removes it with the rest of `gsplat/`, so call the export again when it is needed.

| Return | When |
|--------|------|
| `DDBERR_NONE` | Done |
| `DDBERR_INVALIDARGS` | An argument is `NULL` or empty, the entry is not a Gaussian splat, or its format is not converted (`.ksplat`, `.sog`, `.rad`) |
| `DDBERR_NOTFOUND` | The entry is not in the dataset or has no `model.rad` yet |
| `DDBERR_BUILDINPROGRESS` | A build or another export of the entry holds its lock |
| `DDBERR_EXCEPTION` | The dataset file is missing or cannot be decoded |
| `DDBERR_RETRYABLE` | The disk is (nearly) full (`DDBGetLastErrorReason`) |
| `DDBERR_CANCELED` | The cancel token was canceled; nothing is written |
| `DDBERR_BUSY` | Database contention |

The export is in the `cancellable` list of `DDBGetCapabilities()`.

## Training data of a Gaussian splat

`DDBExportSplatTrainingData(ddbPath, folder, outFolder, optionsJson, progress, progressUserData, &output)` is `ddb gsplat --training-data` on a dataset. It reads the ODM project that is in `folder` of the dataset (an entry path; `NULL`, `""` and `"."` are the root) and writes the [training data](/developers/cli/cookbook.mdx#training-data-from-an-odm-project) into `outFolder`, a folder of the filesystem (UTF-8) that is created if it is missing. It must be missing or empty, outside the dataset and neither the folder of the project, a folder that holds it nor a folder inside it (links are resolved), so that no file the export did not make is replaced: a COLMAP sparse model in `sparse/0`, the images in `images/` and `georef.json`. The project needs `cameras.json`, `odm_report/shots.geojson`, `images/` and `odm_georeferencing/coords.txt`, and has its point cloud in `odm_georeferencing/odm_georeferenced_model.laz` or `odm_filterpoints/point_cloud.ply`. The call only reads the dataset.

| Argument | Meaning |
|----------|---------|
| `optionsJson` | `NULL`, `""` or `{}` for the defaults, else an object with `maxImageSize` (the longest side of the images in pixels; 0, the default, exports the originals) and `maxPoints` (the most points of the model; 100000 by default, 0 writes none). Both are whole numbers from 0, and `maxPoints` is at most 10000000. A member that is not known, or not a whole number in range, is refused with `DDBERR_INVALIDARGS`. |
| `progress`, `progressUserData` | Optional (`NULL` for none). Called with the fraction done (0 to 1) and the phase (`cameras`, `points`, `images` or `model`), one call at a time; a non-zero return cancels the call. |

On success `output` is a JSON object, to free with `DDBFree`: `{"warnings": ["..."], "images": 412, "points": 98211}`. The warnings are what a user should know before training: images that were left out, an approximated lens, no point cloud, images that mostly look straight down.

| Return | When |
|--------|------|
| `DDBERR_NONE` | Done |
| `DDBERR_INVALIDARGS` | An argument is `NULL` or empty, an option is refused, or `outFolder` is a file, is not empty, is in the dataset or is the project folder, holds it or is inside it |
| `DDBERR_NOTFOUND` | `folder` is not in the dataset |
| `DDBERR_EXCEPTION` | A file of the project is missing or unusable (the message names it, `coords.txt` included), or no image can be exported (the message gives the reasons) |
| `DDBERR_CANCELED` | The cancel token was canceled, or the progress callback returned non-zero |
| `DDBERR_BUSY` | Database contention |

A failed or canceled call may leave a partial `outFolder`: delete it. The export is in the `cancellable` list of `DDBGetCapabilities()`.

## Spectral indices of a raster

`DDBGetRasterInfo` reports, in `indexLayer`, the spectral indices `DDBRenderRasterIndex` (the WMS index layer) can render from the raster: a subset of `NDVI`, `NDRE`, `NDWI`, `SAVI`, `EVI`, in that order, `[]` when there are none. The bands come from the raster's sensor profile; a raster without named bands and with five data bands or more is read as R, G, B, RedEdge, NIR. SAVI and EVI are listed only for floating-point rasters. `DDBRenderRasterIndex` refuses an index the list does not hold, with the reason.

The formula list of `DDBGetRasterMetadata` marks the formulas a raster cannot compute with `"disabled": true` and a `disabledReason` ("Requires bands: ..." or, for SAVI, OSAVI and EVI on an integer raster, "... needs reflectance values"). See [How DroneDB reads the bands](/developers/cli/cookbook.mdx#how-dronedb-reads-the-bands).

Since 2.1, `DDBGetRasterMetadata`, `DDBMemoryTileEx`, `DDBExportRaster` and `DDBExportRaster2` return `DDBERR_INVALIDARGS` for a formula that does not exist or whose bands the raster lacks, with the reason in `DDBGetLastError()` (`Requires bands: RN` for NDVI on an RGB raster: use VARI), instead of drawing one colour. `CELSIUS` and `KELVIN` still render an elevation model. The thumbnail export returns `DDBERR_EXCEPTION`. Offer only the formulas that the raster has.

## Raster values

Since 2.2 the values of a raster that the library reports (value info, point values, area statistics, profiles and contours) are **physical values read from the source file**: `raw × scale + offset` in the unit of the band, without the pixels that the file masks or marks as no data. A band stored as tenths of a degree gives `29.1`, not `291`. A host that applied a scale or an offset itself drops it, and compares saved values against 2.2 output. The default render of a raster of several bands that is not Byte, and of a single band, stretches over the mean ± 2.33 standard deviations clamped to the range, so thermal and elevation rasters are no longer washed out.

One options type carries the settings of every raster value export:

```c
typedef struct {
    uint32_t structSize;   /* sizeof(DDBRasterOptions) */
    uint32_t flags;        /* DDB_RASTER_OPT_NODATA 0x1, DDB_RASTER_OPT_BBOX 0x2: which fields are set */
    double nodata;         /* with DDB_RASTER_OPT_NODATA: a finite value that replaces the NoData of every band */
    double bbox[4];        /* with DDB_RASTER_OPT_BBOX (value info only): minLon, minLat, maxLon, maxLat (WGS 84) */
    const char *formula;   /* an index for the stretch of value info; CELSIUS or KELVIN for a thermal value; or NULL */
} DDBRasterOptions;
```

A `NULL` options pointer means every option unset. Set `structSize` and every field explicitly: a later version may append fields, and a library that does not know them refuses a struct whose unknown bytes are not zero (`DDBERR_INVALIDARGS`), as it refuses an invalid option. These ten exports take it, and all ten are cancellable:

| Export | What it adds to the export without `Ex` |
|--------|------------------------------------------|
| `DDBGetRasterValueInfoEx(file, options, &out)` | `nodata`, `bbox`, `formula` (the index of the stretch) |
| `DDBGetRasterPointValueEx(file, lon, lat, options, &out)` | A point in map coordinates (WGS 84); the answer adds `lon` and `lat` |
| `DDBGetRasterAreaStatsEx(file, minLon, minLat, maxLon, maxLat, options, &out)` | A window in map coordinates (the pixels whose centre is inside it; `bounds` are those pixels) |
| `DDBGetRasterPointValuePixelEx(file, x, y, options, &out)` | A pixel of a raster without a map (an R-JPEG), with `nodata` and a thermal `formula`; the answer adds `unit` |
| `DDBGetRasterAreaStatsPixelEx(file, x0, y0, x1, y1, options, &out)` | A rectangle of pixels of such a raster, with the same options |
| `DDBGetRasterProfileEx(file, lineString, samples, options, &out)` | `nodata` |
| `DDBGenerateContoursEx(…, options, &out)` | `nodata`; levels, statistics and elevations in the units of the band, without the masked pixels |
| `DDBGenerateMemoryThumbnailEx2(…, options, &buffer, &size)` | `nodata`: a pixel equal to it is transparent and out of the stretch |
| `DDBMemoryTileEx2(…, options, &buffer, &size)` | The same, for a tile |
| `DDBExportRaster3(…, progress, userData, options)` | The same, for an exported GeoTIFF |

The map-coordinate queries use the one conversion from longitude and latitude to the pixel of the file that the profile, the region render and the stockpile tools use. A window across the antimeridian is refused unless the raster crosses it. A point or window outside the raster, or whose pixels all lack a value, returns `DDBERR_INVALIDARGS` with the reason, as do a formula that does not exist, a thermal formula that is not `CELSIUS` or `KELVIN`, and invalid options. `DDBGetRasterValueInfoEx` reports the exact range of the pixels that have a value in the unit of the band (`valueMin`, `valueMax`), `pixelCount`, `validPixelCount`, `windowPixelCount`, the default `stretch` (one `{min, max}` per band, one for an index, none for a Byte raster of several bands), `nodata`, `nodataOverridden`, `scale` and `offset`, and `nodataInvalid` when the NoData value is not a number that the type of the band can hold.

The statistics behind these values are exact raw statistics, keyed by the version of the file, the band and the effective NoData value, kept in a version 2 sidecar; an old or approximate sidecar is replaced. A confined worker can read them: the artifact check no longer creates the cache folder. A **thumbnail** of a raster larger than 2048 × 2048 pixels whose exact statistics are not stored yet takes its stretch from a bounded sample (an overview within the budget, else whole blocks on a lattice) so that it stays within the time limit of the thumbnail worker, and never stores that sample. Value info, tiles, contours and the COG build stay exact, so such a thumbnail can differ slightly from the stretch of value info until the raster is built.

## Index files

The library keeps idle index connections open between calls and leaves committed changes in `.ddb/dbase.sqlite-wal`. Call `DDBCheckpoint` before copying `dbase.sqlite` without its WAL, and `DDBReleaseConnections` before deleting, moving or replacing a dataset folder from the same process. Details and settings: [CLI reference](/developers/cli/reference.mdx#library-hosts-index-connections).

## Output contract

The JSON outputs Registry reads (listings, entries, build manifest, STAC, raster information, capabilities, effective configuration) have JSON Schemas and golden fixtures in DroneDB's `tests/contract` folder. Field names and types are frozen within a major version; times are integer Unix seconds.
