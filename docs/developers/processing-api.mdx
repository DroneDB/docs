Long jobs on a dataset run as **tasks** on the processing platform of Registry: exports, ZIP
downloads, photogrammetry, imports, archive extraction, rescans and splat exports. A task runs
in the background (Hangfire), off the HTTP request, and the server keeps its state, log and
result. Hub uses the same API for the **Tasks** panel.

To configure the platform on your own server (limits, processing nodes, which tools are on), see
[Processing nodes & feature gating](/docs/self-hosting/processing-nodes).

## Concepts

- **Tool**: a named, versioned operation, for example `raster-export`. A tool declares the
  access it needs (read or write), whether it makes a file to download (an **artifact**), and a
  JSON Schema of its parameters.
- **Task**: one run of a tool on a dataset, with a `taskId`.
- **Artifact**: the file that a task makes, for example a `.tif` or a `.zip`. The server deletes
  it after a time (`ProcessingPlatform:ArtifactTtlHours`).
- **Deduplication**: a task with the same tool, version and parameters, sent again within the
  look-back window (`DedupLookbackHours`), returns the existing task (`200` with
  `deduplicated: true`) instead of a new one (`202`). Send `force: true` to run it again.

## Task states

```text
Created → Indexing → Enqueued → Scheduled → Processing → Succeeded
                                                       → Failed
                                                       → Deleted
```

`Created`, `Indexing`, `Enqueued`, `Scheduled` and `Processing` are active. `Succeeded`, `Failed` and
`Deleted` are terminal. `GET /sys/features` lists the states with `terminal` in `taskStates`.

## Endpoints

All task endpoints are below `/orgs/{orgSlug}/ds/{dsSlug}/tasks`.

| Request | What it does |
|---|---|
| `GET …/tasks/tools` | The tools of this dataset: id, version, title, required access, artifact flag, JSON Schema, and `hidden`, `disabled`, `disabledMessage` |
| `POST …/tasks` | Start a task: `202`, or `200` for a deduplicated one |
| `GET …/tasks` | The tasks of the dataset: `toolId`, `state`, `skip`, `take` (default 50, at most 200). Sends an `ETag`; `If-None-Match` gets `304` while nothing changed. |
| `GET …/tasks/events` | Server-sent events (`text/event-stream`): a `tasks` event when the task list changes, and a comment every 25 seconds to keep the connection open |
| `GET …/tasks/{id}` | State, progress, log tail and artifact of a task |
| `GET …/tasks/{id}/log?since={cursor}` | The log lines after a cursor |
| `GET …/tasks/{id}/result` | Download the artifact (range requests work) |
| `DELETE …/tasks/{id}` | Cancel a task. Only its owner or an administrator can, and a signed-in user can cancel their own task of a tool that needs only read access (for example `raster-contours` and `raster-export`) without write access to the dataset. |
| `POST …/tasks/{id}/retry` | Run a failed task again from the beginning. `409` for a succeeded, cancelled or committed task, and for one that already runs. The request is checked as a new submit (`400`, `409`, `507`) |
| `POST …/tasks/{id}/delete` | Remove one terminal task and its artifact from the history. `400` for a task that is still active. |
| `POST …/tasks/clear?toolId=` | Remove every terminal task (of one tool, with `toolId`) and its artifacts |

Administrators list the tasks of every user and dataset with
`GET /sys/tasks?toolId=&state=&userId=&skip=0&take=50`. Add `sortField` (`createdAt`, `state` or `toolId`;
default `createdAt`) and `sortOrder` (`asc` or `desc`; default `desc`): the server sorts the whole list, with
the newest task first and then the id as the tie-break, before it pages, so the total and the pages do
not change. Another value answers `400` with `errors.sortField` or `errors.sortOrder`. The per-dataset endpoints above work for
them on any dataset.

### Start a task

```http
POST /orgs/my-org/ds/survey-2026/tasks
Content-Type: application/json

{
  "toolId": "raster-export",
  "path": "odm_orthophoto/odm_orthophoto.tif",
  "params": { "formula": "VARI", "colormap": "rdylgn" },
  "force": false
}
```

`version` is optional: without it the current version of the tool runs.

| Status | Meaning |
|---|---|
| `202 Accepted` | A new task. `Location` is its status URL. |
| `200 OK` | `deduplicated: true`: an earlier task with the same request. |
| `400` | Unknown tool, invalid parameters or an invalid path. The answer gives the reason. An output path that is also one of the inputs is a `400` too (`The output '<path>' is also one of the input files: choose another output path.`). |
| `403` | The tool is disabled or hidden for you (see [Feature gating](#feature-gating)), or you do not have the access it needs |
| `409` | The output cannot be written: a file or folder of that name exists and the tool did not get `overwrite: true` (see [Existing outputs](#existing-outputs)), or a task of the dataset that has not finished writes the same output path |
| `413`, `429` | A limit: the output would be too large, or you have too many tasks running or queued |
| `503` | Another start of a task in this dataset is being checked: try again after the seconds of `Retry-After` (2) |

```json
{
  "taskId": "abc123",
  "toolId": "raster-export",
  "version": "1",
  "deduplicated": false,
  "statusUrl": "/orgs/my-org/ds/survey-2026/tasks/abc123",
  "resultUrl": "/orgs/my-org/ds/survey-2026/tasks/abc123/result",
  "estimatedOutputBytes": 52428800
}
```

#### Existing outputs

`align-raster`, `merge-multispectral` and `mask-borders` (and `import-file` and `archive-extract`,
for a destination that is a file) refuse to replace a file that exists. Without `overwrite: true`
the start answers `409` ProblemDetails: the message is `A file or folder named '<name>' already
exists in this folder`, and `conflictPath` is the path of the existing entry, in its own letter
case (names are compared without regard to case). A folder is never replaced.

With `overwrite: true` the tool replaces the file only if it exists when the replace is decided,
and the library puts the new file in its place in one step: a task that fails or is cancelled
leaves the file that was there unchanged. A file that another user creates after the request is
refused and kept (the `409` or a failed task). Before this rule, `import-file` and `archive-extract`
answered `400` for a destination that is a file; they answer `409` now.

### Follow a task

```json
{
  "taskId": "abc123",
  "toolId": "raster-export",
  "version": "1",
  "state": "Processing",
  "progress": { "percent": 42, "phase": "Warping bands" },
  "createdAt": "2026-06-13T10:00:00Z",
  "startedAt": "2026-06-13T10:00:05Z",
  "finishedAt": null,
  "logCursor": 18,
  "logTail": ["[10:00:05] Starting export ...", "..."],
  "artifact": null,
  "error": null
}
```

A `build` task has a `progress` too, from a Registry that runs libddb 2.3 or later (`DDBBuildEx2`, see the [library](/developers/library.mdx#builds)): `percent` stays 0 until libddb has measured something, and `phase` is what libddb names: the type of the entry (`georaster`, `pointcloud`, `model`, `vector`, `gaussiansplat` or `tiles3d`), then `warping`, `overviews` and `compressing` for a raster (no `warping` when it is on the tile grid already), then `publishing`, and `done` at the end. The phase never goes back and the percent never goes down. With an older libddb a build task has no percent. An `Enqueued` build of a dataset whose build runs has the `phase` `Waiting behind <path>`.

When the task succeeds, `artifact` holds `sizeBytes`, `sha256`, `resultUrl` and `expiresAt`.
`GET …/result` returns the file with `Content-Disposition: attachment` and the SHA-256 as its
`ETag`. It works only when the state is `Succeeded` and the tool makes an artifact.

When the task fails, `state` is `Failed` and `error` says why, for example
`"The file is damaged or not a valid GeoTIFF"`. The last line of the log is the same reason,
after `Failed: `. Server paths are hidden: the dataset folder reads `[dataset]` and other paths
`[server path]`. In `GET …/tasks` each task has `error` and `errorType`, the type of the error.

Each task of `GET …/tasks`, of `/sys/tasks` and of `GET …/tasks/{id}` has four fields that say what a
row can offer:

| Field | Meaning |
|-------|---------|
| `actions` | What the caller may do with the task: `cancel`, `retry`, `delete` and `viewLog`. A caller who may not touch the task gets an empty list. A reader with no write access gets only `viewLog`, and also `cancel` for their own task of a tool that needs only read access (`raster-contours`, `raster-export`). A task that has saved its result has no `cancel` and no `retry` |
| `targetLabel` | The files of the task in words, as the tool says them, or `null` |
| `waitingForNode` | `true` while a processing node holds the task in its queue. The `state` filter `Enqueued` includes such a task |
| `cancelledBy` | The name of the user who cancelled a `Deleted` task, or `null` |

To read the log as it grows, pass the `cursor` of each answer as `since` of the next request:

```json
{ "cursor": 25, "lines": ["[10:00:10] Band 1/4 done", "..."], "truncatedFromTail": 0 }
```

## Feature gating

An administrator can disable or hide a tool, or allow it only for some roles or organizations.
Gating only narrows the access that a tool needs; it never widens it. The answers show it:

| Endpoint | What you see |
|---|---|
| `GET /sys/features` | `taskTools[]` with `hidden`, `disabled` and `disabledMessage`, without the organization rule |
| `GET …/tasks/tools` | The same fields, with the organization rule of this dataset |
| `POST …/tasks` | A hidden or disabled tool answers `403` with `disabledMessage` (or a default message), whatever the client sends |

A client hides a tool with `hidden: true` and greys it out with `disabled: true`, with
`disabledMessage` as the reason. The `403` of the server decides in every case. The settings are
in [Processing nodes & feature gating](/docs/self-hosting/processing-nodes).

## Tools

The tools that a server offers are in `GET …/tasks/tools`, with the JSON Schema of their
parameters. These are the tools of Registry 3.0.

| Tool | Title | Access | Artifact |
|---|---|---|---|
| `build` | Build | Write | No |
| `raster-export` | Export raster (GeoTIFF) | Read | `.tif` |
| `raster-contours` | Contour lines | Read | `.geojson` |
| `bulk-download` | Download archive (ZIP) | Read | `.zip` |
| `align-raster` | Align GeoTIFF to reference | Write | No |
| `merge-multispectral` | Merge multispectral bands | Write | No |
| `mask-borders` | Mask Borders | Write | No |
| `archive-extract` | Extract archive | Write | No |
| `rescan-index` | Rescan index | Write | No |
| `import-file` | Import file from URL | Write | No |
| `import-dataset` | Import dataset | Write | No |
| `photogrammetry` | Photogrammetry (NodeODX) | Write | No |
| `splat-spz-export` | Export splat as .spz | Read | No (a build artifact) |
| `splat-training-export` | Export splat training data | Read | `.zip` |

The tools without an artifact change the dataset: their new files are indexed, and the files
that can be built are built in the background.

### build

Builds an entry, like `POST …/build`, as a task you can follow.

```json
{ "path": "odm_orthophoto/odm_orthophoto.tif", "force": false }
```

Both are optional. Without `path` it builds the pending entries.

### raster-export

Exports a raster as a GeoTIFF with display settings applied: a preset, a band selection, a
spectral index, a colormap, a rescale. Memory stays bounded at any size.

```json
{
  "path": "odm_orthophoto/odm_orthophoto.tif",
  "preset": null,
  "bands": null,
  "formula": "VARI",
  "bandFilter": null,
  "colormap": "rdylgn",
  "rescale": "-1,1",
  "fileName": null,
  "nodata": null,
  "bbox": null
}
```

`path` is required. The others are optional. A `formula` that the raster cannot compute is
refused with `400` before the task is queued, for example `NDVI is not available for this raster:
Requires bands: RN` on an RGB orthophoto. Use `VARI` on RGB, and `NDVI` on a raster with a
near-infrared band. An unknown formula answers `Unknown formula: <name>`. `rescale` is `min,max`: two finite numbers within the
range of a 32-bit float with `min` below `max`; another value is `400` before the task is queued. The tile, thumbnail and analysis endpoints that take a `rescale` check it the same way. With a thermal `formula` they take `rescaleUnit` too (`K`, `C` or `F`, since DroneDB 2.3.0, which Registry 3.0 requires): a `rescale` written in that unit is converted to the unit of the formula, as Hub does when a user changes the unit after setting a range.

An export larger than the limit of the server (`MaxExportSizeBytes`, `exportLimitBytes` of `GET …/raster-value-info`)
is refused with `400` before the task is queued: `Export output exceeds maximum allowed size (… > …)`. The
ProblemDetails has the numbers: `estimatedExportBytes` and `exportLimitBytes`. The size is
estimated as the number of pixels that have a value × 4 bytes, with no compression factor
(`estimatedExportBytes` of value info).

`nodata` is a finite number that replaces the no-data value of the bands. `bbox` is a window,
`[minLon, minLat, maxLon, maxLat]` in WGS 84: the task exports the pixels of the raster whose centre is
inside it, at the resolution of the raster, in its coordinate system and with the position of the window.
The estimate and the limit apply to the window (the same estimate as value info with `bbox`). A box that is not four
finite numbers, or that has no pixel of the raster, is `400` at `errors.bbox`. A window needs libddb 2.3 or later: on an
older server it is `400` at `errors.bbox` (`Exporting the visible extent needs libddb 2.3 or later`),
because the older library would export the whole raster. `rasterExportWindow` of `GET /sys/features` says whether the
server takes it. The file is in the coordinate system of the source (not Web Mercator). With a `formula` it is an 8-bit RGBA picture of the style, not the index values; without one it is the selected bands as 8-bit values scaled to `rescale`, with no colormap. This is what Hub's
**Export** and **Visible extent** buttons send.

### raster-contours

Generates the contour lines of a raster as a GeoJSON file, with progress and a cancel. The body is that of
[`POST …/contours`](#raster-values), checked the same way at submit (a `400` before the task is queued).

```json
{
  "path": "odm_dem/dsm.tif",
  "interval": 5,
  "count": null,
  "baseOffset": 0,
  "minElev": null,
  "maxElev": null,
  "simplifyTolerance": 0,
  "bandIndex": 1,
  "nodata": null,
  "formula": null,
  "fileName": null
}
```

`path` is required. `interval` wins over `count`; `formula` is `CELSIUS` or `KELVIN` for a thermal raster (and, since DroneDB 2.3, `FAHRENHEIT`) and
an index is ignored. The result is the FeatureCollection of `POST …/contours` (a LineString per line, with `elev`), the
artifact of the task: read it from `GET …/tasks/{id}/result`. Progress goes from the `statistics` phase to `levels` and
`lines`. A large raster is read from the COG of its build, as at the endpoint. The result has at most 100,000 lines. When
the lines were cut it has `"truncated": true` and `featureCap`, and the log of the task says
`Contours truncated at 100000 lines`. Since DroneDB 2.3 the result has `truncated` and `featureCap` (the 2.2 result stopped
at 100,000 lines without saying it), and a server with it reports progress while the lines are made.

### bulk-download

Packs some entries, or the whole dataset, into a ZIP.

```json
{ "paths": ["images/DJI_0001.JPG", "images/DJI_0002.JPG"], "archiveName": "my-selection.zip" }
```

Without `paths` the ZIP holds the whole dataset, `.ddb` folder included. Small selections can be
downloaded directly with `GET …/download` instead. Selections larger than
`bulkDownloadAsyncThresholdBytes` of `GET /sys/features` should use this task.

### align-raster

Aligns a GeoTIFF to a reference GeoTIFF (phase correlation and NCC) and adds the result to the
dataset as a new file: a lossless GeoTIFF in the coordinate system, pixel size and bands of the
source (only its georeference changes). It is indexed and built afterwards to get its map tiles.

```json
{
  "sourcePath": "survey-2026.tif",
  "referencePath": "reference-2024.tif",
  "outputPath": "survey-2026-aligned.tif",
  "mode": "similarity",
  "overwrite": false
}
```

`sourcePath`, `referencePath` and `outputPath` are required. `mode` is `similarity` (4 degrees of
freedom, default) or `translation` (2, faster). `overwrite` (default `false`) replaces an output
that exists. `POST …/align/validate` checks the inputs first.

### merge-multispectral

Merges single-band GeoTIFFs into one multi-band GeoTIFF in the dataset (a capture of a MicaSense, Sequoia or DJI camera keeps its camera metadata, so Plant Health opens it).

```json
{ "paths": ["red.tif", "green.tif", "blue.tif", "nir.tif"], "outputPath": "merged.tif", "overwrite": false }
```

`paths` (at least two, in band order) and `outputPath` are required. `overwrite` (default
`false`) replaces an output that exists.
`POST …/merge-multispectral/validate` and `…/preview` check the inputs first.

### mask-borders

Makes the border pixels of a georaster transparent and adds the result as `<name>_masked.tif` next to the
source, in the same folder. The task is named after the new file (`targetLabel`), counts in the storage
quota and is rolled back like the other tools that add files. The new file is indexed and its build is
queued as a child of the task.

```json
{ "path": "odm_orthophoto/odm_orthophoto.tif", "near": 15, "white": false, "overwrite": false }
```

`path` is required. `near` (0 to 255, default `15`) is how far from black (or white) a pixel can be and still
be border, `white` masks the white border, and `overwrite` (default `false`) replaces a masked copy that
exists: without it the start is `409`, as for the other tools, and a second mask of the same output while
one runs is `409` too.

### archive-extract

Extracts an archive of the dataset. Each file is indexed as if it was uploaded, and the files
that can be built are built.

```json
{ "sourcePath": "uploads/batch.zip", "destPath": "extracted/", "deleteArchive": false, "overwrite": false }
```

`sourcePath` is required. `destPath` is the root by default. The archive formats are in
`archiveExtensions` of `GET /sys/features`.

### rescan-index

Reads the metadata of the entries again (EXIF, location, type), for example after an upgrade
that reads more.

```json
{ "types": "image,geoimage", "extensions": "jpg,tif", "stopOnError": false }
```

All optional. An entry must match both filters. An unknown type or an invalid extension (such
as `*.dwg`) is a `400`. Without a filter, the task clears the build cache and builds the whole
dataset again. With a filter, it builds only the rescanned entries that can be built, one at a
time; a failed build does not fail the task.

To rescan every dataset that has matching entries, an administrator sends
`POST /sys/rescan`:

```bash
curl -X POST -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
     -d '{"extensions": ["dwg", "dxf"]}' https://registry.example.com/sys/rescan
```

| Field | Description |
|---|---|
| `types` | Entry types, for example `["vector"]` |
| `extensions` | File extensions, for example `["dwg", "dxf"]` |
| `organizationSlug` | Only this organization (optional) |
| `datasetSlug` | Only this dataset; needs `organizationSlug` (optional) |
| `stopOnError` | Stop a dataset at its first error (default `false`) |

At least one of `types` and `extensions` is required. The answer is `202` with the id of a
background job, which starts a `rescan-index` task for each dataset with matching entries. The
tasks run on the build queue.

### import-file

Downloads one file from an `http` or `https` URL into the dataset, then indexes and builds it.
The download refuses private addresses and keeps to the storage budget.

```json
{
  "url": "https://example.com/data/orthophoto.tif",
  "fileName": "orthophoto.tif",
  "folder": "imports",
  "overwrite": false,
  "username": null,
  "password": null,
  "sizeBytes": null
}
```

`url` and `fileName` are required. `password` must be an encrypted credential.
`POST …/import/verify-url` checks a URL first; `POST …/import/url` starts the import.

### import-dataset

Fills a new, empty dataset from another Registry (`registry`) or from an archive URL
(`archive-url`).

```json
{
  "sourceType": "registry",
  "budgetBytes": null,
  "params": { "…": "the parameters of the source" }
}
```

`sourceType` and `params` are required. The parameters depend on the source. The organization
endpoints do the whole flow:

| Request | What it does |
|---|---|
| `GET /orgs/{orgSlug}/import/sources` | The source types this server offers |
| `POST /orgs/{orgSlug}/import/verify` | Checks a source without creating anything |
| `POST /orgs/{orgSlug}/import/browse` | Lists the organizations or datasets of a `registry` source |
| `POST /orgs/{orgSlug}/import` | Creates an empty dataset and starts the import |

To copy datasets or organizations between Registries as an administrator, see
[Import from another Registry](/developers/api/workflows.mdx#import-from-another-registry).

### photogrammetry

Sends images to a NodeODX processing node and extracts the results (orthophoto, DEM, point
cloud, model…) into the dataset, or into a new dataset.

| Parameter | Type | Description |
|---|---|---|
| `folder` | string | The folder to take the images from (default: the whole dataset) |
| `images` | string[] | The image paths, instead of a folder |
| `nodeId` | string | The processing node (default: the first one) |
| `name` | string | The task name on the node |
| `options` | `{name, value}[]` | NodeODX options, passed as they are, for example `[{"name": "dsm", "value": true}]` |
| `destPath` | string | The folder for the results. Required unless `createNewDataset` is `true`. |
| `createNewDataset` | boolean | Put the results in a new dataset |
| `newDatasetName` | string | The slug of the new dataset (generated when missing) |
| `newDatasetOrgSlug` | string | Its organization (default: the same one) |
| `newDatasetVisibility` | string | `PRIVATE` (default), `UNLISTED` or `PUBLIC` |

The results come as one archive from the node and are extracted into the dataset; there is no
separate artifact. The nodes and their options:

| Request | What it does |
|---|---|
| `GET /sys/processingNodes` | The nodes you can use: id and title (never the URL or the token) |
| `GET /sys/processingNodes/{nodeId}/options` | The options of a node, read live from it. Each has `name`, `type`, `domain`, `help` and `value`, the default of the node |
| `GET /sys/processingNodes/{nodeId}/status` | Whether the node can be reached, its engine, `taskQueueCount`, the tasks it runs plus the tasks that wait, and `maxParallelTasks` |

The `help` of an option comes with its placeholders filled in (the choices, the default and `%%`).
Common NodeODX options: `dsm`, `dtm`, `3d-tiles`, `fast-orthophoto`, `feature-quality` (`ultra`, `high`,
`medium`, `low`, `lowest`), `pc-quality` and `orthophoto-resolution`. Read the list of your node, as the
options depend on its version.

The progress of a run follows the stages of the node: its `phase` is one of `opensfm`, `openmvs`,
`filtering points`, `meshing`, `texturing`, `georeferencing`, `DEM`, `orthophoto`, `report` and
`postprocess`, and the percent does not go back. A failed or cancelled run is removed from the node after its
output is copied to the log of the task (see
[Processing nodes & features](/self-hosting/processing-nodes.mdx#nodeodx-nodes-for-photogrammetry)).

### splat-spz-export

Makes the `.spz` of a built Gaussian splat for other tools. The task has no file of its own:
DroneDB keeps the `.spz` in the build of the entry (role `gsplat.export`).

```json
{ "toolId": "splat-spz-export", "path": "scenes/site.ply", "params": {}, "force": true }
```

- `path` is required: a Gaussian splat whose build is complete. A path that is not in the
  dataset or not built is `404`; an entry that is not a splat is `400`.
- A `.ksplat`, `.sog` or `.rad` source is accepted by the request and fails in the task.
- Send `force: true` to run it again instead of getting the earlier task. DroneDB returns the
  file it has when it is not older than the dataset file (the log says
  `The .spz file was already exported`).
- The task runs in the build queue and holds the build lock of the entry. It waits while a
  build or another export of the entry runs.

When the state is `Succeeded`, download the file:

```http
GET /orgs/{orgSlug}/ds/{dsSlug}/build-artifact?path=scenes/site.ply&role=gsplat.export
```

The answer is the `.spz` named after the entry (`site.spz`), with range requests. `404` says to
run the export first when the entry has no `gsplat.export` yet. A rebuild of the splat removes
the file. The same query with `role=gsplat.lod` downloads `site.rad`.

### splat-training-export

Exports the ODM project in a folder of the dataset as the training data of a Gaussian splat: a
COLMAP sparse model in metres, the images and the georeference, in one ZIP. See
[Training data from an ODM project](/developers/cli/cookbook.mdx#training-data-from-an-odm-project).

```json
{
  "toolId": "splat-training-export",
  "path": "odm_project",
  "params": { "maxImageSize": 1600, "maxPoints": 100000, "fileName": "site-training-data.zip" },
  "force": true
}
```

`path` is the folder of the project; empty or missing for the root. A folder that is not in the
dataset is `404`; a file is `400`.

| Parameter | Meaning |
|---|---|
| `maxImageSize` | The longest side of the images in pixels; `0` or missing keeps the originals. 0 to 1048576. |
| `maxPoints` | The most points of the sparse model; `100000` when missing, `0` writes none. 0 to 10000000. |
| `fileName` | The ZIP name. Default `<folder>-training-data.zip` (`<dataset>-training-data.zip` for the root); `.zip` is added when missing. |

A negative value or one above its limit is a `400` before the task is queued. `progress.phase`
is `cameras`, `points`, `images`, `model`, then `archiving`. `GET …/tasks/{id}/result` downloads
the ZIP: `sparse/0/cameras.bin`, `images.bin`, `points3D.bin`, `images/` and `georef.json` at its
root. Each warning (images left out, an approximated lens, no point cloud, nadir images) is a
`Warning: …` line of the log: read them from `logTail` or the log endpoint.

## Other processing endpoints

Some quick operations are plain endpoints of a dataset, not tasks:

| Request | What it does |
|---|---|
| `POST …/mask-borders` | Starts a background job that writes `<name>_masked.tif` next to a GeoRaster. Body `{ "path", "near": 15, "white": false, "overwrite": false }`; an existing masked copy is `409` without `overwrite`. Needs write access. Hub uses the `mask-borders` tool instead; this endpoint keeps working for other clients. |
| `POST …/mask-borders/check` | Whether the masked file exists already, and its path |
| `POST …/contours` | Contour lines of a raster, as GeoJSON, in one request. Hub runs every contour request as the [`raster-contours`](#raster-contours) task instead; this endpoint keeps working for other clients |
| `GET …/raster-value-info`, `GET …/raster-point-value`, `GET …/raster-area-stats`, `POST …/raster-profile` | The range of a raster, and its values at a point, in an area and along a line: see [Raster values](#raster-values) |
| `POST …/stockpile/detect`, `…/stockpile/detect-all`, `…/stockpile/calculate` | Stockpile footprint and volume on an elevation model: see [Stockpiles](#stockpiles) |

Their parameters are in the [API reference](/developers/api/reference.mdx) of the server.

### Stockpiles

All three take a JSON body with `path` (the elevation model) and need read access.

| Request | Body and answer |
|---|---|
| `POST …/stockpile/detect` | `lat`, `lon` (WGS 84, required), `radius` (metres, default `50`) and `sensitivity` (0 to 1, default `0.5`): the footprint of the pile around the click, down to its foot, with `confidence` and the estimated volume |
| `POST …/stockpile/detect-all` | `sensitivity` (0 to 1, default `0.5`), `minAreaM2` (the smallest pile in square metres, default `5`) and `maxResults` (default `50`, at most `500`): `{ "stockpiles": [...], "totalFound", "sensitivityUsed", "minAreaUsed" }`: the piles of the raster, the biggest volume first and at most `maxResults`, each with `id`, `polygon`, `estimatedVolume`, `confidence`, `baseElevation`, `centroid`, `areaM2` and `pixelCount`. `totalFound` is the length of the returned list (counted after the cut), so a list as long as `maxResults` may be cut. No pile is an empty list |
| `POST …/stockpile/calculate` | The volume of a polygon (GeoJSON, WGS 84), with a base plane method |

The volumes are in m³, the areas in m² and the elevations in metres whatever the unit of the raster.

### Raster values

The raster endpoints read the **source file** of the entry, not its build, and give the values of
the band in its own unit (`raw × scale + offset`), leaving out the pixels that the file masks or
marks as no data. They need read access. All of them take `path` and, optionally:

| Parameter | Meaning |
|---|---|
| `nodata` | A finite number that replaces the no-data value of every band for this request. In the body of `raster-profile` and `contours`. Value info says in `nodata` which value applies and in `nodataOverridden` whether it is yours; `nodataInvalid` is `true` when the value of the file cannot be held by the type of the band. |
| `formula` | A vegetation index for the default stretch of value info, or `CELSIUS`, `KELVIN` or (since DroneDB 2.3) `FAHRENHEIT` to read a thermal value in that unit. The library converts from the unit of the band, so the values, the range of value info, the unit in the answer and the contours are in the unit you ask. A formula that is not a thermal one is `400` for a point, an area and a profile |

| Request | Parameters and answer |
|---|---|
| `GET …/raster-value-info` | `bbox` (`minLon,minLat,maxLon,maxLat`, WGS 84) is optional. The exact range of the valid pixels (`valueMin`, `valueMax`), `pixelCount`, `validPixelCount`, `windowPixelCount`, `unit`, `nodata`, `scale`, `offset`, the default colour `stretch` (one `{min, max}` per band, one for an index, none for a Byte raster of several bands), and `estimatedExportBytes` and `exportLimitBytes` of a [raster export](#raster-export). With `bbox` the estimate is that of the window. For a thermal raster it also has `isThermal`, `isDirectValue` and, when a calibration turns raw counts into temperatures, a [`calibration`](#thermal-calibration). |
| `GET …/raster-point-value` | `lon` and `lat` (WGS 84): the value of the pixel under the point, with `lon` and `lat` in the answer. For a raster without a map (a radiometric JPEG) send `x` and `y`, a pixel of its raw thermal grid, and the answer has its `unit`. |
| `GET …/raster-area-stats` | `bbox` (WGS 84): `min`, `max`, `mean`, `stddev`, `median` and `pixelCount` of the pixels of the file whose centre is inside the window. For a radiometric JPEG send `x0`, `y0`, `x1` and `y1` (pixels). |
| `POST …/raster-profile` | Body `{ "path", "lineString", "samples", "nodata", "formula" }`: `lineString` is a GeoJSON LineString in WGS 84 and `samples` is clamped to 2 to 4096. Each sample has `distance` (metres), `value` (`null` where the raster has none), `lon` and `lat`. |
| `POST …/contours` | The contour lines of a band in the units of the raster, without the masked pixels. Takes `nodata`. |

Map coordinates and pixels are never mixed: a request with both is `400`, and so are pixel
coordinates on a georeferenced raster (`errors.x`, `errors.x0`) and a `bbox` that is not four finite
numbers inside longitude -180 to 180 and latitude -90 to 90. A point or a window outside the raster,
or with only pixels that have no value, is `400` with the reason (so is a pixel of a radiometric picture whose raw count has no temperature in the calibration). A `formula` that does not exist, or
that the raster cannot compute (`Requires bands: RN`), is `400` too. One conversion from longitude
and latitude to the pixel of the file serves all of these endpoints, the stockpile tools and the
elevation profile. The first value info of a large raster computes its exact statistics and keeps
them (keyed by the version of the file, the band and the effective no-data value), so the next one is fast.

#### Thermal calibration

A radiometric picture (an R-JPEG: FLIR, or a DJI thermal camera) has no map, so its value info, point value and area statistics take pixels (`x`, `y`) of its raw thermal image, and answer in the unit of the `formula` you send (`CELSIUS` by default in Hub). Since DroneDB 2.3:

- A **FLIR** picture has a `calibration` only when the file gives the five Planck constants (`planckR1`, `planckB`, `planckF`, `planckO`, `planckR2`). They come from the CameraInfo record of the FLIR FFF data in the file, and from the XMP only when the file has no such record. The raw image is the one of the RawData record (16-bit counts); a RawData record stored as a PNG image is not decoded yet. There is no default by make and model.
- The `calibration` adds, only when the file gives them, `emissivity`, `objectDistance`, `reflectedApparentTemperature` and `atmosphericTemperature` (°C), `relativeHumidity` (a fraction, 0 to 1), `irWindowTemperature`, `irWindowTransmission` and, since 2.3, `atmosphericTransAlpha1`, `atmosphericTransAlpha2`, `atmosphericTransBeta1`, `atmosphericTransBeta2` and `atmosphericTransX`. A raw count outside the calibration has no value (`400`), not `0` °C.
- A **DJI** R-JPEG (M2EA, H20T, H20N, M30T, M3T and M3TD, H30T and any model with raw thermal data) is read from its raw thermal data, but its counts need DJI's own conversion, which DroneDB does not have yet. Its answers have `unit` `""`, `isDirectValue` `false` and no `calibration`: raw counts, not temperatures.
- A thermal formula (`CELSIUS`, `KELVIN`, `FAHRENHEIT`) on values without a calibration is `400` at a point, an area and a profile, with the reason in the message: **No thermal calibration: …** the 8-bit colours of the preview of a picture whose raw thermal data cannot be read; raw sensor counts without the Planck constants in the file; or the raw counts of a DJI R-JPEG, which need DJI's own conversion. A sample of a profile whose raw count has no temperature is `null`.
- A thermal UInt16 band with a scale or an offset (the Landsat encoding) holds physical values: it keeps its unit and its thermal formulas and has no Planck calibration. A UInt16 band without them holds raw counts without a unit.
- The raw counts of a picture without a unit are not temperatures: a client does not label them in °C. Rescan the image entries after the upgrade so that the wide and zoom pictures of DJI thermal drones lose `sensorCategory` `thermal` and the DJI thermal pictures gain it.

A thumbnail with a `colormap` of such a picture is drawn from the temperatures of its raw thermal data, in the unit of the `formula`, over the `rescale` or else its minimum to maximum, not from the colour preview.

A [thumbnail](/developers/library.mdx#raster-values) of a raster larger than 2048 × 2048 pixels whose
exact statistics are not stored yet takes its colour stretch from a bounded sample, so that it comes
within the time limit of the thumbnail worker. Value info, tiles, contours and the COG build stay
exact, so such a thumbnail can differ a little from the stretch of value info until the raster is
built.
