---
title: "Users & organizations API"
description: "Manage users, roles, storage quotas, organizations and their members through the Registry API."
---

These endpoints manage the accounts of a Registry. Most of them need an administrator. For the
same tasks in the admin pages of Hub, see [Users, organizations & roles](/docs/self-hosting/users).
To sign in and get a token, see [Authentication](/developers/api/authentication.mdx).

The examples use a self-hosted Registry:

```bash
REG=http://localhost:5000
AUTH="Authorization: Bearer $ADMIN_TOKEN"
```

## Users

| Request | Access | What it does |
|---|---|---|
| `GET /users` | Admin | All users: `userName`, `email`, `roles`, `organizations` |
| `GET /users/detailed` | Admin | All users with storage, organization and dataset counts |
| `POST /users` | Admin | Create a user (JSON) |
| `PUT /users/{userName}` | Admin | Change the e-mail and the roles (JSON) |
| `POST /users/{userName}/disable` | Admin | Disable a user: they cannot sign in, and their sessions lose access at once |
| `POST /users/{userName}/enable` | Admin | Enable a disabled user |
| `DELETE /users/{userName}` | Admin | Delete a user (query `successor`, `conflictResolution`) |
| `DELETE /users` | Admin | The same, with a form body (`UserName`, `Successor`, `ConflictResolution`) |
| `POST /users/changepwd` | Signed in | Change your own password (form `oldPassword`, `newPassword`). Returns a new token. |
| `PUT /users/{userName}/changepwd` | Signed in | Change a password (JSON `currentPassword`, `newPassword`). Only an administrator may omit `currentPassword`, to reset the password of a user. |

A refused password change is a `400` `ValidationProblemDetails` that names the field in `errors`, also when
the form call sends `oldPassword`: `errors.currentPassword` is `["The current password is incorrect."]`, and
`errors.newPassword` has the password rules that the new password breaks, as one sentence without the
Identity codes. `detail` keeps the whole message. Read the field, not the text: the Hub shows each message
under its field. A refusal that concerns no field (for example a locked user) has no `errors` member.

### Create a user

```bash
curl -X POST -H "$AUTH" -H "Content-Type: application/json" $REG/users -d '{
  "userName": "jdoe",
  "email": "jdoe@example.com",
  "password": "a-long-password-1"
}'
```

`userName` and `password` are required. User names are 1 to 127 lowercase letters (`a-z`) and
digits. Users that LDAP or an external authentication service signs in keep the wider character
set of their directory. The password must follow the password policy of the server
(`passwordPolicy` in `GET /sys/features`). The e-mail address is optional; an address that is
not valid answers `400`. `roles` is optional: every role in it must exist, and it cannot hold
`deactivated`. The answer is the new user.

When Registry creates a user, it also creates a personal organization with the user name as its
slug, unless `EnableDefaultUserOrganization` is off in the configuration.

### Change e-mail and roles

```bash
curl -X POST -H "$AUTH" -H "Content-Type: application/json" $REG/users/roles -d '{ "roleName": "editor" }'
curl -X PUT -H "$AUTH" -H "Content-Type: application/json" $REG/users/jdoe -d '{
  "email": "jdoe@example.com",
  "roles": ["editor"]
}'
```

`roles` is required; `email` is optional: omitted (or `null`) it keeps the current address, an empty
string removes it, and anything else must be one valid address (`errors.email` of the `400`). Under
external authentication (`userManagement` false) an update that does not change the e-mail is
accepted. The user gets the roles of the list: Registry adds the missing ones and
removes the others. It checks every role first, and a role that does not exist answers `400`
before anything changes. The list never adds or removes `deactivated`: a list that would add it
answers `400`, and a disabled user stays disabled. Use the disable and enable endpoints instead.
The e-mail address is checked only when it changes.

### Disable and enable a user

```bash
curl -X POST -H "$AUTH" $REG/users/jdoe/disable
curl -X POST -H "$AUTH" $REG/users/jdoe/enable
```

Both answer `204`, also when the user is already in that state, and `404` for an unknown user.
`disable` answers `400` for your own account and for the last active administrator. A disabled
user cannot sign in, and their tokens lose access at once. Their data is kept. Both endpoints
also work for LDAP and external authentication users.

### Delete a user

```bash
curl -X DELETE -H "$AUTH" "$REG/users/jdoe?successor=archive&conflictResolution=2"
```

| Parameter | Description |
|---|---|
| `successor` | The user who gets the organizations, datasets and upload batches. Without it, all the data of the user is deleted. |
| `conflictResolution` | When a dataset name exists in the organization of the successor: `0` stop, `1` overwrite, `2` rename (default) |

The answer says how many organizations and datasets were transferred or deleted, and how many
batches were deleted.

## Roles

| Request | Access | What it does |
|---|---|---|
| `GET /users/roles` | Signed in | The role names |
| `POST /users/roles` | Admin | Create a role: JSON `{ "roleName": "editor" }`. A role name is 1 to 127 lowercase letters (`a-z`) and digits, as a user name; another name is `400` with `errors.roleName` |
| `DELETE /users/roles/{roleName}` | Admin | Delete a role (`204`). The system roles `admin` and `deactivated` cannot be deleted (`400`). A role created before the name rule, with a `/` or a sign in its name, is found as written and then unescaped, so it can be deleted. |

The system roles are listed in `systemRoles` of `GET /sys/features`. `admin` is the system
administrator: `PUT /users/{userName}` grants and removes it. `deactivated` blocks sign-in: only
the disable and enable endpoints change it. A role can also limit who may use a processing tool
(see [Feature gating](/developers/processing-api.mdx#feature-gating)).

## Storage and user metadata

| Request | Access | What it does |
|---|---|---|
| `GET /users/storage` | Signed in | Your storage: `{ "total", "used" }` in bytes. `total` is `null` without a limit. |
| `GET /users/{userName}/storage` | Admin | The storage of a user |
| `GET /users/meta` | Signed in | Your metadata |
| `GET /users/{userName}/meta` | Admin | The metadata of a user |
| `POST /users/{userName}/meta` | Admin | Set the metadata of a user (a JSON object) |

The storage limit of a user is the metadata key `maxStorageMB`. It applies when the storage
limiter is on (`storageLimiter` in `GET /sys/features`). It is the quota of the **owner of the
organization** that counts, whoever writes: when the owner is over the quota, a member of the organization
who uploads, pastes, copies, imports or starts a task that adds files gets `507` too. An administrator
owner has no limit, and an organization without an owner is unlimited.

```bash
curl -X POST -H "$AUTH" -H "Content-Type: application/json" $REG/users/jdoe/meta \
     -d '{ "maxStorageMB": 10240 }'
```

## Preferences and notifications

These act on the signed-in user.

| Request | What it does |
|---|---|
| `GET /users/preferences` | The Hub preferences, one property per section (`{}` when none) |
| `PATCH /users/preferences` | Set the sections in the JSON body and keep the others. A section set to `null` goes back to the defaults. The `notifications` section has two fields, merged one by one: `builds` (`none`, `all` or `failed`) and `tasks` (`none`, `all` or `failed`). A field that is missing or `null` keeps the stored value, so a client that sets one does not change the other. |
| `GET /users/notifications/status` | `{ canReceiveEmail, reason }`: `reason` is `emailDisabled` (the server sends no e-mail), `noAddress` (the account has no valid address) or `null` |

## Organizations

| Request | Access | What it does |
|---|---|---|
| `GET /orgs` | Signed in | The organizations you can read, by name then slug (all of them for an administrator). With `ownedOnly=true`: the organizations you own, belong to, or that are Public. |
| `GET /orgs/public` | Anyone | The public organizations |
| `GET /orgs/{orgSlug}` | Read access | One organization |
| `POST /orgs` | Signed in | Create an organization (form fields) |
| `PUT /orgs/{orgSlug}` | Write access | Change it (form fields). Only an administrator may change the owner. |
| `DELETE /orgs/{orgSlug}` | Delete access | Delete it **and all its datasets** |
| `GET /orgs/{orgSlug}/locations` | Read access | `[{ "slug", "name", "bbox" }]`, one per dataset: `bbox` is `[minLon, minLat, maxLon, maxLat]` in WGS84, or `null` |

```bash
curl -X POST -H "$AUTH" $REG/orgs \
     -F slug=project-alpha -F name="Project Alpha" -F description="Main project" -F isPublic=true
```

| Field | Description |
|---|---|
| `slug` | Required. 2 to 128 lowercase letters, digits, `_` and `-`; starts with a letter or digit; no `--`. |
| `name` | Required |
| `description` | Optional |
| `isPublic` | Public: anyone, signed in or not, can read the organization and its public datasets, and `GET /orgs` lists it to every signed-in user |
| `owner` | A user id. Only an administrator may set an owner other than the caller. |

An organization has `slug`, `name`, `description`, `creationDate`, `owner`, `isPublic`,
`datasetCount` and `lastModified`. `datasetCount` and `lastModified` are `null` for callers who
are not the owner, a member or an administrator, and in `GET /orgs/public`. `/locations` hides
unlisted datasets from those callers.

A signed-in user who is not a member reads a Public organization like a visitor: read-only, and
without its private datasets. Writing needs membership. While the owner of a Public organization is
disabled, those who are not members can neither read it nor see it in the list.

## Organization members

The owner, a member with the `Admin` permission, or a system administrator manages the members.
These endpoints work when organization member management is on
(`organizationMemberManagement` in `GET /sys/features`). When it is off, they answer `403` to
everyone, system administrators included.

| Request | What it does |
|---|---|
| `GET /orgs/{orgSlug}/members` | The members and their permissions, sorted by user name (letter case does not matter) |
| `POST /orgs/{orgSlug}/members` | Add a member: JSON `{ "userName": "jdoe", "permissions": 1 }` |
| `PUT /orgs/{orgSlug}/members/{userName}` | Change the permission: JSON `{ "permissions": 2 }` |
| `DELETE /orgs/{orgSlug}/members/{userName}` | Remove a member |

`POST /orgs/{orgSlug}/members` takes the exact user name: the list of users (`GET /users`) is for
administrators only, so an owner does not need it. It answers:

| Status | When |
|---|---|
| `204` | The user is now a member |
| `400` | The `userName` is empty |
| `401` | The caller is not signed in |
| `403` | The caller cannot manage the members (a member without `Admin`, an outsider), or member management is off |
| `404` | No user has that name; the message names it |
| `409` | The user is already a member |

| `permissions` | Name | Can |
|---|---|---|
| `0` | ReadOnly | Read the datasets and the organization |
| `1` | ReadWrite (default) | Also upload, change and build |
| `2` | ReadWriteDelete | Also delete datasets |
| `3` | Admin | Also manage the members |

### The organizations of a user

Administrators can manage memberships from the user side too:

| Request | What it does |
|---|---|
| `GET /users/{userName}/orgs` | The organizations of a user, with `isOwner`, `permissions`, `grantedAt`, `grantedBy` |
| `POST /users/{userName}/orgs` | Add the user to an organization: JSON `{ "orgSlug": "project-alpha", "permissions": 1 }` |
| `PUT /users/{userName}/orgs/{orgSlug}` | Change the permission: JSON `{ "permissions": 3 }` |
| `DELETE /users/{userName}/orgs/{orgSlug}` | Remove the user from the organization. The owner cannot be removed. |

## External authentication and LDAP

When the Registry signs users in through LDAP or an external authentication service, the
identities belong to that service. Local user management is then off (`userManagement: false`
in `GET /sys/features`): users are not created, changed or deleted locally, passwords cannot be
changed through the API (`403`), and roles and profile come from the service at each sign-in. See
[LDAP / Active Directory](/docs/self-hosting/ldap) and the
[configuration](/docs/self-hosting/configuration).
