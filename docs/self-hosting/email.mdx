Registry sends e-mail through an SMTP server: the test e-mail, the
[update e-mails](/self-hosting/update-check.mdx#update-e-mails) to administrators and the build notifications to
users. E-mail is off by default. While it is off, Registry writes each e-mail it would send to the
log and drops it, and everything else works as before.

## Turn on e-mail

1. Add the `Smtp` section to `AppSettings` in `appsettings.json` (all keys:
   [Configuration → Smtp](/self-hosting/configuration.mdx#smtp)):

   ```json
   "Smtp": {
     "Enabled": true,
     "Host": "smtp.example.com",
     "Port": 587,
     "Security": "StartTls",
     "UserName": "registry@example.com",
     "FromAddress": "registry@example.com",
     "FromName": "Acme Drone Data"
   }
   ```

2. Set the password as the environment variable `AppSettings__Smtp__Password`, not in the file.
3. Set [`ExternalUrlOverride`](/self-hosting/configuration.mdx#externalurloverride) to the public URL of
   Registry. E-mails link to it and load the logo from it. Without it, e-mails have no links, no
   logo and no icon, and Registry logs a warning at start.
4. Restart Registry. The start log shows `E-mail: smtp.example.com:587 (StartTls)`.
5. [Send a test e-mail](#test-the-settings).

Registry checks the section when it starts. A missing `Host` or `FromAddress`, an address that is
not valid, or a `UserName` without a `Password` stops Registry with a message that names the key.
To check a file without a start, run `Registry.Web <storage folder> --check`.

:::warning Every Registry service needs the settings

A request queues an e-mail, and the process that runs background jobs sends it. With processing
nodes, every node needs the same `Smtp` settings and password. In the Docker Compose setup all
services read the same `appsettings.json`: set `AppSettings__Smtp__Password` on every service
(the Compose file has the line, commented out). An e-mail that reaches a process with e-mail off
fails in the Hangfire dashboard with the reason. Requeue it after you fix the settings.

:::

## Connection security

| `Security` | Port | Use it for |
|------------|------|------------|
| `StartTls` (default) | 587 | Most providers. The connection is upgraded with STARTTLS. If the server does not offer STARTTLS, the send fails: Registry never falls back to clear text. |
| `SslOnConnect` | 465 | Providers that use TLS from the first byte ("SMTPS"). |
| `None` | 25 | Only a relay on the same host or on a trusted private network (for example a local Postfix). |

`ValidateServerCertificate` is `true` by default. Set it to `false` only for a test server with a
self-signed certificate. The certificate must still be for the configured `Host`.

## Examples

A provider with SSL on connect:

```json
"Smtp": {
  "Enabled": true,
  "Host": "smtp.provider.example",
  "Port": 465,
  "Security": "SslOnConnect",
  "UserName": "user@your-domain.example",
  "FromAddress": "user@your-domain.example"
}
```

A local relay without login:

```json
"Smtp": {
  "Enabled": true,
  "Host": "localhost",
  "Port": 25,
  "Security": "None",
  "FromAddress": "registry@your-domain.example"
}
```

:::tip

Many providers accept only a `FromAddress` on a domain that you verified with them (SPF and DKIM
records). If the test e-mail is refused with a 5xx reply about the sender, verify the domain with
the provider.

:::

## Test the settings

An administrator can send a test e-mail. It uses the current settings and waits for the answer of
the server:

```bash
curl -X POST https://registry.example.com/sys/email/test \
  -H "Authorization: Bearer <admin token>" \
  -H "Content-Type: application/json" \
  -d '{"to": "you@example.com"}'
```

| Answer | Meaning |
|--------|---------|
| `204` | The server accepted the e-mail. |
| `400` | E-mail is off, or the address is not valid. |
| `502` | The server refused the e-mail or could not be reached. The `detail` gives the reply of the server, for example `The mail server smtp.example.com:587 replied 535: authentication failed`. |

In the Hub, **Send me a test** on the [E-mail templates](#edit-the-build-notification-template)
card sends a sample build or task notification to your own address.

## Health check and clients

- When e-mail is on, the health report (`/health`) has an `SMTP health check` entry. It connects
  and logs in, but sends nothing. A failure is **Degraded**, not Unhealthy: Registry works without
  e-mail, so a mail outage does not make an orchestrator restart it. The result is kept for 5
  minutes, so a monitor that polls often does not log in each time.
- The anonymous `GET /sys/features` has `emailEnabled`. The Hub reads it to hide what needs e-mail
  (for example the **Notifications** tab of the preferences). It shows nothing else of the
  settings.

## Delivery and retries

Most e-mails go out through a background job (Hangfire, `default` queue):

- When the server cannot be reached, times out or answers "try again later" (a 4xx reply), the job
  tries again 5 times, after 1 minute, 5 minutes, 15 minutes, 1 hour and 3 hours.
- When the server refuses the e-mail for good (a 5xx reply, a refused login, a certificate that is
  not valid), the job fails at once. The Hangfire dashboard shows the reason.

The log records each e-mail with its message id, the number of recipients and their domains, never
the full addresses.

## Branding

Every e-mail looks like the Hub of the instance. Registry reads the
[Hub settings](/self-hosting/configuration.mdx#hub-ui-customization); there is no separate setting for e-mails.

| Setting | Use in the e-mail | When it is not set or not usable |
|---------|-------------------|----------------------------------|
| `HubOptions.AppName` | The name in the header and the footer ("Sent by …"), the sender name when `Smtp.FromName` is not set, and `{{appName}}` | `DroneDB` |
| `HubOptions.AppLogo` | The logo in the header, 40 px high. It must be PNG, JPEG or GIF: mail clients block SVG. An absolute `https` URL or a path of the instance such as `/branding/logo.png`. | The icon (next row) |
| `HubOptions.Favicon.AppleTouchIcon`, else `HubOptions.Favicon.Favicon32` | A small icon next to the name, only when there is no PNG, JPEG or GIF logo | The name as text |
| `HubOptions.Favicon.ThemeColor` | The accent: the top bar, the links and the buttons. Only `#rgb` or `#rrggbb`; other values are ignored. | The Hub blue `#0070e0` |

- The label of a button is white or near-black, whichever reads better on the accent.
- When the accent is too light for text on white (a yellow, for example), links use a darker shade
  of it. The bar and the buttons keep the accent.
- "Failed" is always red, "Waiting for files" always amber and "Completed" always green.
- A stock instance (no `AppName`, no `AppIcon`, no `AppLogo` or the shipped
  `/images/logo-banner.svg`) shows the DroneDB logo `/images/email-logo.png`. An instance with its
  own name, icon or logo never shows the DroneDB logo.
- A path such as `/branding/logo.png` and the DroneDB logo need `ExternalUrlOverride`. Without it,
  only a logo or icon with an absolute URL can show, and there are no links.

:::tip A Hub with an SVG logo

The Hub header can keep an SVG `AppLogo`. The e-mails then show the `AppleTouchIcon` next to the
name. Put the files in `{StoragePath}/branding/` (`data/branding/` with the default
`StoragePath`) and reference them as `/branding/…`: the folder survives Hub upgrades.

:::

## Build notifications

Users can get an e-mail when the builds of their files end. Each user chooses **None** (the
default), **All** or **Failed or waiting for files** in the Hub. What each choice sends, and what
the e-mail looks like, is on [Build notification e-mails](/docs/hub-guide/account/build-notifications).

### Requirements

- E-mail is on. While it is off, the Hub does not show the **Notifications** tab.
- The account has a valid e-mail address and is not deactivated. Users cannot change their own
  address: an administrator sets it ([Edit a user](/self-hosting/users.mdx#edit-a-user)).
- `ExternalUrlOverride` is set. Without it, the e-mail is still sent, without links and logo.

### When an e-mail is sent

Registry e-mails the user who asked for the build: the user who uploaded the file or asked to build
it again, the user who started the task that made the file (for example an archive extraction),
the user whose build failed (for an automatic retry), or the user whose build waited for files.
Builds that Registry starts by itself (a rescan, a check of the built files) send nothing.

- **Final failures only.** While Registry retries a build automatically (no disk space, a tool
  timeout), nothing is sent. When the retries give up, the
  [pending builds job](/self-hosting/configuration.mdx#processpendingbuildscron) can still build the file later.
- **Grouped.** The first build of a user that ends starts a wait of
  [`BuildNotifications:DigestMinutes`](/self-hosting/configuration.mdx#buildnotifications) (5 minutes). Then one
  e-mail lists every build of that user that ended in the wait. Before it sends, Registry reads the
  setting of the user again.
- **After a restart.** When Registry stops during a wait, the daily
  [`JobIndexCleanupCron`](/self-hosting/configuration.mdx#jobindexcleanupcron) job sends the builds that waited
  for more than one hour. It also deletes the records of sent builds after 30 days, but keeps the
  record of a build that still waits for files. With that job turned off, none of this happens.
- **Waiting for files.** A build that misses a companion file (an `.mtl`, a texture, the `.dbf` of a
  `.shp`) sends one "Waiting for files" line with the missing names, once for the same content of
  the file. All Registry processes share this record in the database, so a restart or a second
  process does not send it again. The build runs when a file with a missing name arrives, and its
  end goes to the user whose build waited.
- **Where.** A build ends on the process that runs it: every processing node needs the `Smtp`
  settings.

## Task notifications

A user can also get one e-mail when a task they started ends: the preference `notifications.tasks`
(**Send task notifications** in the Hub: **None**, the default, **Failed only** or **All**). What each
choice sends is on [Build notification e-mails](/docs/hub-guide/account/build-notifications). It is a
preference of the user, not a configuration key. The [requirements](#requirements) are the same.

- Registry e-mails the user who submitted the task, when it ends **Failed** or **Succeeded**. It sends
  one e-mail for each run, not a digest. A retry of a failed task starts a new run and a new e-mail.
- It sends nothing for a cancelled task, for the build tool (see [Build notifications](#build-notifications)),
  for a child task, for a task that Registry starts by itself, for a deleted dataset, for a user without an
  address, or for a user who cannot read the dataset.
- The e-mail shows the reason of a failure without URL query strings, credentials or the values of
  `token`, `password`, `secret` and `key`.
- The link opens the **Tasks** tab of the dataset (`?tab=tasks`). When the failed run had created its
  dataset and Registry removes it, the link opens the organization.
- The e-mail is sent by the process that ends the task: every processing node needs the `Smtp` settings.

## Edit the build notification template

In the Hub, open the user menu, then **Configuration**. The **E-mail templates** card is there when
e-mail is on. Choose the **Template**: **Build notifications** or **Task notifications**. It shows the **Subject**
and the **Body**, with a **Default** or **Custom** tag. Below, `build-notification` is the template of the builds;
[the template of the tasks](#the-task-notification-template) is `task-notification`.

<Screenshot id="self-hosting/email--templates" />

- Click a placeholder to insert it at the cursor of the field you were in. Placeholders that only
  the body can use are disabled while the cursor is in the subject.
- **Preview** shows the text that is not saved yet with sample data (three builds for the build template,
  a failed photogrammetry run for the task template), with the real layout and branding: the subject, the HTML and
  the plain text.
- **Send me a test** sends the same sample to the address of your account at once. Your account
  needs an address.
- **Reset to default** removes the saved text, after you confirm.
- **Save** saves the text. A text with an error is refused with a message that names the problem,
  for example `Unknown placeholder {{foo}} in the body`.

<Screenshot id="self-hosting/email--received" />

Registry keeps the saved text in `{StoragePath}/.email-templates.json`, which all processes share.

The built-in text:

```text title="Subject"
{{appName}}: {{summary}}
```

```text title="Body"
Hello {{user}},

{{summary}} on {{appName}}.

{{builds}}

{{link}}

To change which build e-mails you get, open your notification settings: {{preferencesLink}}
```

### Placeholders

| Placeholder | Value | In the subject |
|-------------|-------|----------------|
| `{{appName}}` | The application name (see [Branding](#branding)) | Yes |
| `{{user}}` | The name of the user | Yes |
| `{{summary}}` | The counts in words, for example `2 builds failed, 1 waiting for files, 3 completed` | Yes |
| `{{failedCount}}` | Number of failed builds | Yes |
| `{{waitingCount}}` | Number of builds that wait for files | Yes |
| `{{completedCount}}` | Number of completed builds | Yes |
| `{{datasets}}` | The datasets of the builds, as `organization/dataset`, separated by commas | Yes |
| `{{builds}}` | The list of builds, with the reason of each failure and the missing files of each build that waits | No |
| `{{link}}` | A link to the dataset, or to the Hub when the builds are in more than one dataset | No |
| `{{preferencesLink}}` | A link to the notification settings of the user | No |

Names are case-sensitive (`{{appName}}`, not `{{appname}}`). Spaces inside the braces are allowed
(`{{ user }}`).

### How the text is rendered

Registry makes an HTML part and a plain-text part from the same text.

- The body is plain text. A blank line starts a paragraph; a single line break is a line break.
  Spaces at the start and end of a line are removed.
- Registry escapes every value and every word in the HTML part. The text cannot add HTML, styles
  or scripts: `<b>` shows as `<b>`.
- `{{builds}}` is a block of its own. In HTML it is a table with the dataset (a link), the file
  with the reason of a failure or the missing files, and the result. In plain text it is a list,
  for example `- Failed: flight-2/cloud.laz (acme-surveys/survey-2026)` with `Reason: …` on the
  next line. Failed builds come first, then the builds that wait for files, then the completed
  builds, each in the order they ended.
- `{{link}}` alone in its paragraph is a button: **Open the dataset**, or **Open** and the
  application name for more than one dataset. In a sentence, `{{link}}` and `{{preferencesLink}}`
  are links that show the address. In plain text they are the address. Only `http` and `https`
  addresses become links.
- Without `ExternalUrlOverride` there are no links, and a paragraph that uses `{{link}}` or
  `{{preferencesLink}}` is left out with all its words. Put each link in a paragraph with only the
  words that belong to it.
- The subject is one line: line breaks and runs of spaces become one space.

Registry refuses a text when the subject or the body is empty, the subject is longer than 200
characters or the body longer than 16384, a `{{` has no `}}`, a placeholder is not in the table,
or the subject uses a placeholder of the body only.

A saved text that a newer Registry no longer accepts (for example with a placeholder that was
removed) is not used: Registry sends the built-in text, logs a warning, and the card shows the
built-in text. Edit the text and save it again.

### The task notification template

The built-in text:

```text title="Subject"
{{appName}}: {{task}} {{result}}
```

```text title="Body"
Hello {{user}},

Your task "{{task}}" on {{dataset}} {{result}}.

Files: {{label}}

Reason: {{error}}

{{datasetNote}}

Duration: {{duration}}

{{link}}

To change which task e-mails you get, open your notification settings: {{preferencesLink}}
```

| Placeholder | Value | In the subject |
|-------------|-------|----------------|
| `{{appName}}` | The application name | Yes |
| `{{user}}` | The name of the user | Yes |
| `{{task}}` | What the task is, for example `Photogrammetry (NodeODX)` | Yes |
| `{{label}}` | The files of the task, as the task list names them | Yes |
| `{{dataset}}` | The dataset, as `organization/dataset` | Yes |
| `{{result}}` | How it ended: `completed` or `failed` | Yes |
| `{{error}}` | Why the task failed | No |
| `{{duration}}` | How long it ran, for example `17 min 4 s` | Yes |
| `{{datasetNote}}` | A sentence that the dataset the run created is removed, because the task failed | No |
| `{{link}}` | A link to the **Tasks** tab of the dataset, or to the organization when the dataset is removed. Alone in its paragraph it is a button | No |
| `{{preferencesLink}}` | A link to the notification settings of the user | No |

A paragraph that uses a placeholder that has no value is left out with all its words: `{{error}}` for a task
that completed, `{{label}}` for a task without files, `{{datasetNote}}` unless a failed run created its dataset.
The rules of [how the text is rendered](#how-the-text-is-rendered) are the same.

### Template API

The card uses these endpoints, for administrators only (`403` for other users). The template name
is `build-notification` or `task-notification`.

| Method | Endpoint | Body | Answer |
|--------|----------|------|--------|
| GET | `/sys/email/templates` | — | The templates: `name`, `title`, `isDefault` |
| GET | `/sys/email/templates/{name}` | — | `subject`, `body`, `isDefault`, `defaultSubject`, `defaultBody` and the `placeholders` (`name`, `description`, `inSubject`). `404` for an unknown name |
| PUT | `/sys/email/templates/{name}` | `{"subject", "body"}` | Checks and saves the text; answers like GET. `400` names the problem |
| DELETE | `/sys/email/templates/{name}` | — | Removes the saved text; answers like GET, with `isDefault: true` |
| POST | `/sys/email/templates/{name}/preview` | `{"subject", "body"}` | The text (not saved) with the sample builds or the sample task: `{"subject", "text", "html"}`. `400` names the problem |
| POST | `/sys/email/templates/{name}/test` | `{"subject", "body"}` | Sends the sample to the calling administrator. Answers like [the test e-mail](#test-the-settings); `400` also when the account has no valid address |
