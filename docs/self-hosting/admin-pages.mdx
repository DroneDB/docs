Administrators have more entries in the Hub user menu. Click your user name at the top right (an administrator
sees an **Admin** badge next to it). The menu has two groups, **Administration** and **Account**:

| Entry | Opens |
|-------|-------|
| **Manage Users** | [User Management](/self-hosting/users.mdx) (`/admin/users`). Only with local accounts. |
| **Tasks** | The [Tasks](#tasks) page (`/admin/tasks`) |
| **Configuration** | The [Configuration](#configuration) page (`/admin/config`) |
| **Hangfire** | The [Hangfire dashboard](#hangfire) (`/hangfire`), in a new tab |
| **API Docs** | The interactive API reference (`/scalar/v1`), in a new tab |

<Screenshot id="self-hosting/admin-pages--menu" />

Users who are not administrators do not see these entries, and the pages refuse them.

## Configuration

The **Configuration** page shows the settings that this Registry runs with, grouped in sections. It
does not change them: Registry reads its settings from `appsettings.json` and the environment
when it starts. Use the page to read the effective values and to prepare a change.

<Screenshot id="self-hosting/admin-pages--config" />

At the top are two cards:

- **Usage and contact**: how this deployment is used and an optional contact address for the
  [update check](/self-hosting/update-check.mdx#declare-how-you-use-registry). **Save** stores them. It is
  off, with its reason as a tooltip, when nothing changed, and it checks the e-mail address and the consent
  before it sends.
- **E-mail templates**: the build notification e-mail. Shown only when e-mail is on. See
  [Edit the build notification template](/self-hosting/email.mdx#edit-the-build-notification-template).
  **Save** stores the text.

Below the cards, each section has a **Custom** tag when a value differs from the default, or a
**Default** tag. Each field shows its description and a tag: **Default**, **Modified** (you
changed it on the page), **Set (masked)** or **Not set** for secrets, and **Read-only** for
information such as the instance ID or the effective host budget. Secrets are never shown: click
**Change** to type a new value.

The sections, in order: Auth & Security, Default Admin, Database & Cache Providers, Storage Paths,
Upload Settings, Download Settings, Cache Expiration, Redis Configuration (applies only with the Redis cache provider), Cron
Jobs, Password Policy, Hub Options, Organization Management, Thumbnails, Export & Zip, LDAP /
Active Directory, E-mail (SMTP), Build notifications, Update check, Processing Platform, Tool
Gating, Processing Budget, Host Budget, Import Dataset, Connection Strings, Serilog Logging,
Miscellaneous. Each setting is described in the [Configuration reference](/self-hosting/configuration.mdx).

To change a setting:

1. Edit the values on the page. The page checks what you type, with the rules that the server checks: a
   time span (`d`, `hh:mm:ss` with hours up to 23, such as `00:30:00`), a cron expression (5 or 6 fields,
   a macro such as `@daily`, or a word that turns the job off such as `disabled`) and a JSON value show their
   error under the field while you type, and the header of the section counts them (**2 invalid**). A cron
   field shows the default of the job as its hint (the value that a blank field takes).
2. Click **Copy AppSettings JSON**. While a value is invalid nothing is copied: the page says how many
   fields it refuses and which, and moves the focus to the first one. The clipboard gets the JSON in the shape of
   `appsettings.json`, with the current values and your changes. A secret that is set and that you
   did not change is written as `<CHANGE-ME>`.
3. Put the keys you changed in `appsettings.json` (or set them as environment variables). The copied
   JSON has the shape that Registry reads: keys that the page only groups (**Update check**, **Cron
   Jobs**, **Cache Expiration** …) are direct keys of `AppSettings`, the nested sections (`Smtp`, `HubOptions`,
   `ProcessingPlatform` …) keep their object, and `ConnectionStrings` and `Serilog` are next to
   `AppSettings`, not inside it.
4. Run `Registry.Web <storage folder> --check`, then restart Registry.

**Reset Section** and **Reset to Defaults** undo your edits on the page; they do not change the
server.

## Tasks

The **Tasks** page lists the tasks of every user and dataset: exports, imports, archive
extractions, photogrammetry and the other [tools](/self-hosting/processing-nodes.mdx#tool-gating). Filter by
user (**All users**), by tool (**All tools**) and by state (**All States**); **Clear filters** removes them.
Click the header **State**, **Tool** or **Created** to sort: the server sorts the whole list, newest first
by default, not only the page you see. The filters, the page and the sort stay in the address, so a reload
or a copied link shows the same list. The page shows as many tasks as fit the height of the window. The paginator lists that number as **N (fit)**, and **Tasks per page** chooses another one. Click **Refresh** to load the list again.

<Screenshot id="self-hosting/admin-pages--tasks" />

Each row has the owner and the dataset of the task, and the same actions as the Tasks panel of a
dataset (see [Tasks](/docs/hub-guide/processing/tasks)): open the log, download the result, retry,
**Cancel** (the stop button) for a task that runs, and **Delete from history** (the trash button) for a
finished task. Their confirmation windows are titled **Cancel Task** and **Delete Task**. Deleting a task
also deletes its downloadable result.

Dataset builds also appear here, as **Build** tasks with their file path, owner and log. The background
jobs that run them are in Hangfire.

## Hangfire

The Hangfire dashboard (`/hangfire`) shows the background jobs of every Registry process: the
queues (`builds`, `rebuilds`, `tasks`, `default`), the servers, the jobs that run, wait, failed or
succeeded, the retries and the recurring jobs with their schedule. Only administrators can open it.

<Screenshot id="self-hosting/admin-pages--hangfire" />

Use it to:

- see why a build or an e-mail failed (open the job in **Failed**);
- requeue a failed job after you fix its cause;
- run a recurring job now (**Recurring jobs**, then **Trigger now**), for example the
  [artifact completeness check](/self-hosting/configuration.mdx#artifactcompletenesscheckercron) after an
  upgrade.

The schedules come from the [cron keys](/self-hosting/configuration.mdx#scheduled-jobs) of `appsettings.json`.
A job that you turn off (`disabled`) is not in the list.
